How Linux Really Works

Kernel · User Space · System Calls · Processes · ARMv8 Exception Levels · ECU Boot

1 — Why Do We Need to Understand This?

SELinux lives inside the kernel. To understand why SELinux works the way it does, you must first understand how Linux manages processes, memory, and files — because SELinux hooks into every single one of those operations.

On an automotive ECU, the Linux kernel is the invisible referee that decides whether the OTA daemon can write to the rootfs, whether the CAN gateway can talk to the network stack, or whether a compromised process can read secret keys. SELinux adds an extra layer of rules on top of what the kernel already enforces.

Think of the Linux kernel as the control room of a modern car factory. On the shop floor (user space), robots (processes) request actions — "move this arm", "weld this panel". Every single request goes through the control room (the kernel) which decides if the action is permitted. SELinux is a second guard inside the control room with its own rule book. Even if a robot convinces the first guard, the SELinux guard still checks its own rules before allowing the action.

2 — Kernel Space vs. User Space

Linux memory is split into two regions: kernel space and user space.

Why the boundary matters for SELinux

SELinux policy checks happen inside the kernel — in the LSM (Linux Security Module) hooks. No process in user space can skip them. Even a process running as root (UID 0) must pass SELinux checks before the kernel will carry out its request.

3 — System Calls: The Only Door Into the Kernel

A system call (syscall) is the only legitimate way a user-space program can ask the kernel to do something. There are about 300 syscalls on Linux. Every file open, every network connection, every process creation goes through a syscall.

A syscall is like ordering at a restaurant. You (user-space program) sit at the table and cannot go into the kitchen. You write your order on a slip (the syscall parameters) and hand it to the waiter (the syscall dispatcher). The waiter takes it to the kitchen (kernel), which prepares the result and sends it back. SELinux is a sous chef in the kitchen who reads every order and can refuse to prepare it.

When a process calls open("/etc/ota/private.key", O_RDONLY), the kernel flow is:

1. CPU traps into EL1 (kernel mode) via syscall instruction
2. Kernel resolves the path to an inode
3. VFS calls the LSM hook: security_inode_open()
4. SELinux checks: does OTA daemon's TYPE have "read" permission on private.key's TYPE?
5a. YES → kernel proceeds, returns file descriptor
5b. NO  → kernel returns -EACCES, logs AVC denial to audit log

The key insight: SELinux never sees the syscall directly. It hooks into specific kernel functions that the syscall invokes. The hook is invisible to the process.

4 — Processes: What They Are and How They're Born

A process is a running instance of a program. It has its own memory space, its own file descriptors, and a unique PID (Process ID). On an ECU running Linux, every service — OTA daemon, CAN gateway, diagnostics server — is a process.

A program (binary file on disk) is like a recipe in a cookbook. A process is the actual cooking happening right now — the ingredients are loaded, the chef (CPU) is following the steps, and the kitchen (memory) is in use. The same recipe can be cooked multiple times simultaneously (multiple processes from the same binary). Each cooking session has its own kitchen counter (address space) and its own "currently open cupboards" (file descriptors).

5 — File Descriptors: The Handle for Everything

A file descriptor (fd) is a small integer that the kernel gives back when a process opens a file, socket, pipe, or device. The process uses this number to refer to the open resource in subsequent syscalls.

A file descriptor is exactly like a coat-check ticket. You hand your coat (the file/socket/device) to the coat-check attendant (the kernel). The attendant gives you a numbered ticket (fd: 3, 4, 5…). From that point on, you just say "give me the thing from ticket 3" — you don't need to know the details of where it's stored. When you leave (close the fd), you hand back the ticket and the attendant frees the slot. Numbers 0, 1, and 2 are pre-issued tickets for stdin (keyboard), stdout (screen), and stderr (error output).
FD NumberNameTypically Points To
0stdinTerminal keyboard / /dev/null on ECU daemons
1stdoutTerminal screen / journal on ECU daemons

3+(varies)Any file, socket, pipe, or device the process opened

When SELinux blocks an open() call, the process never receives a file descriptor. The syscall returns -1 with errno = EACCES. No fd means no further operations on that resource are possible.

6 — Daemons: Background Services on the ECU

A daemon is a long-running background process that starts at boot and provides a service. The name comes from Greek mythology — a daemon is a spirit that runs unseen, doing work in the background. On Linux, daemons typically end their name with d: systemd, udevd, sshd, ota_daemon.

A daemon is like a bank vault security guard working a 24-hour shift. They were hired (started at boot), have a specific job description (the service they provide), never interact directly with customers (no terminal), and keep working until the bank closes (system shutdown) or they're explicitly dismissed (SIGTERM). If a guard goes rogue, they have access to the vault all day — this is why daemons need SELinux labels limiting exactly what they can access.

Key daemon properties on an ECU:

  • Started by systemd (PID 1) at boot
  • Stdin/stdout/stderr redirected to /dev/null or systemd journal
  • Run as a specific UID (e.g., ota_user) — not necessarily root
  • Assigned a specific SELinux domain (type) — e.g., ota_daemon_t
  • Never have a controlling terminal

7 — ARMv8 Exception Levels (EL0 – EL3)

On an ARMv8 ECU, the CPU hardware itself enforces privilege boundaries using Exception Levels (EL). These are hardware rings that determine what instructions the CPU will execute.

Linux (with SELinux) runs at EL1. User-space processes run at EL0. On a Xen-based ECU, Xen itself runs at EL2, giving it the power to create isolated VMs for ASIL-rated domains. TrustZone's secure monitor at EL3 handles cryptographic operations and secure boot.

Why does SELinux sit at EL1?

Because the Linux kernel runs at EL1, and SELinux is compiled into the kernel as an LSM. EL1 is privileged enough to intercept every system call from user space (EL0), but isolated from the hypervisor (EL2) and secure monitor (EL3). This means SELinux policy protects the Linux guest's internal structure — not the inter-VM isolation (that's Xen's job via XSM/Flask).

9 — Attack Scenario: Why None of This Is Theoretical

Scenario: Compromised OTA Update on an ECU

An attacker finds a buffer-overflow vulnerability in the OTA update parser. If the ECU had no access controls beyond DAC, here is what they could do:

1
Exploit the OTA parser
Attacker sends a malformed firmware update. The overflow overwrites the return address, hijacking control flow inside ota_daemon.
2
Attempt to open CAN socket
Attacker code calls socket(AF_CAN, SOCK_RAW, CAN_RAW) to create a raw CAN socket — allowing injection of arbitrary CAN frames to other ECUs.
3
Attempt to read secret key
Attacker code opens /etc/ota/private.key to exfiltrate the signing key.
4
SELinux blocks CAN socket creation
The kernel's LSM hook fires on socket(). SELinux checks: does ota_daemon_t have permission to create a can_socket? Policy says NO. Kernel returns -EACCES. AVC denial logged.
5
SELinux blocks key file access
The kernel's LSM hook fires on open(). SELinux checks: does ota_daemon_t have read permission on ota_key_t? Policy says NO. Kernel returns -EACCES. AVC denial logged.
6
Attack is contained within the OTA domain
The attacker is trapped inside ota_daemon_t. They can only access what OTA is legitimately allowed to access — nothing more. The rest of the ECU (CAN bus, key store, safety partition) is unreachable.

10 — Intrusion Detection & Forensics

When SELinux blocks an action, it writes an AVC denial to the kernel audit log. On a vehicle, this log can be forwarded to a V-SOC (Vehicle Security Operations Centre) or stored on a tamper-evident log partition.

Signs of compromise visible in AVC logs:

  • An OTA daemon trying to open CAN sockets (lateral movement attempt)
  • A diagnostics service trying to write to the rootfs (persistence attempt)
  • Any process trying to ptrace another (injection/debugging attempt)
  • Unusual execve denials (trying to run new binaries)

After a security incident, AVC logs tell you:

  • What process attempted the action (source type)
  • What resource it tried to access (target type)
  • What action it tried to perform (permission class)
  • When it happened (timestamp from the audit daemon)
  • Where the process came from (via PID + /proc/PID/exe at time of incident)

Because AVC logs are generated in the kernel and forwarded to a privileged auditd process (which itself has a separate SELinux domain), a compromised user-space process cannot erase them.

# Example AVC denial log entry
type=AVC msg=audit(1715890001.123:42): avc:  denied  { create }
  for  pid=1042
       comm="ota_daemon"
       scontext=system_u:system_r:ota_daemon_t:s0
       tcontext=system_u:system_r:can_socket_t:s0
       tclass=can_socket
       permissive=0

# Decoded:
# - Process: ota_daemon (PID 1042)
# - Tried to: create a CAN socket
# - Its label: ota_daemon_t
# - Target label: can_socket_t
# - Decision: DENIED (not permissive)
# - Timestamp: Unix epoch 1715890001
