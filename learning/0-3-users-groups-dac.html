Users, Groups & DAC Permissions

UIDs · GIDs · Permission Bits · DAC Check · setuid · Why DAC Fails & SELinux Fixes It

1 — Why Do We Need to Understand This?

Before SELinux, Linux used DAC (Discretionary Access Control) as its only permission system. Every file has an owner and permission bits. The owner decides who can access their files — that's why it's called "discretionary" (the owner has discretion).

Understanding DAC is essential because SELinux does not replace DAC — it adds on top of it. Both checks happen. If DAC denies an action, SELinux never even runs. If DAC allows it, SELinux checks its own policy. An access is only permitted if both allow it.

On an ECU, knowing DAC tells you why running everything as root is dangerous — and why SELinux is the mandatory safety net that closes DAC's fundamental design flaws.

DAC is like a house where each room has a combination lock and the room owner sets the combination — they can give it to anyone they choose. The problem: if the owner of the master bedroom gets robbed, the thief now has that combination and can come and go freely. SELinux is a separate security company that installs override locks on every door. Even if the thief has the combination, the security company's system says "this key card is not authorized for this door" — and keeps the door locked regardless.

2 — UIDs and GIDs: Numbers Behind Names

Every process and every file is associated with numeric identifiers. Linux does not care about names internally — it uses numbers.

On a minimal ECU, the /etc/passwd file maps UIDs to names. The kernel only ever uses the number:

# /etc/passwd entries for ECU services (format: name:x:uid:gid:comment:home:shell)
root:x:0:0:root:/root:/bin/sh
ota_user:x:100:100:OTA service:/var/ota:/sbin/nologin
can_gw:x:101:101:CAN gateway:/:/sbin/nologin
v2x_svc:x:102:102:V2X service:/:/sbin/nologin
diag_svc:x:103:103:Diagnostics:/:/sbin/nologin

3 — Permission Bits: The 10-Character Code on Every File

Run ls -l on any file and you see something like -rwxr-xr--. This 10-character string is the file's DAC permission encoding. Let's decode it character by character.

BitOn a Regular FileExample
r (read)Can read the file's contentRead /etc/ota/config.json
w (write)Can modify the file's contentUpdate firmware binary
x (execute)Can run the file as a programExecute /usr/bin/ota_daemon
BitOn a DirectoryExample
r (read)Can list the directory's contents (ls)List files in /etc/ota/
w (write)Can create, delete, or rename files insideWrite new firmware to /data/ota/
x (execute)Can enter the directory and access files inside (needed to use a path)cd /etc/ota/

Tricky rule: You need both r and x on a directory to do a normal ls. With only x you can access files if you know their exact name, but cannot list them. With only r you can list names but cannot open files.

setuid (s)When executed, process runs with the file owner's UID instead of the caller's UIDHigh — root-owned setuid binaries run as root for any caller

The Root Problem

Notice the very first check: Is UID = 0? If yes, DAC grants access without checking any permission bits (for most operations). This means any process running as root can read, write, or execute nearly any file. On an embedded ECU where every daemon runs as root "for convenience", a single compromised service = total system compromise. This is the core DAC weakness that SELinux was designed to fix.

5 — UID Inheritance: How Processes Get Their UID

When a process is created (via fork()), it inherits the UID of its parent. This creates an inheritance chain starting from the kernel's initial process.

In a well-designed ECU, each service has its own dedicated UID. The systemd unit file uses User=ota_user to drop from root to the service account before executing the daemon binary. Even without SELinux, this limits what a compromised daemon can do via DAC. With SELinux, the domain (type) provides the real confinement.

6 — setuid: DAC's Most Dangerous Feature

The setuid bit allows a binary to run with the file owner's privileges rather than the caller's. A setuid binary owned by root runs as root for any user who executes it. This was designed to allow unprivileged users to do specific privileged operations (e.g., changing their own password via /usr/bin/passwd).

setuid is like a spare master key taped to a locker. Anyone who finds the locker (the setuid binary) can use the master key (run as root) just by opening the locker. If the locker is broken (the binary has a vulnerability), an attacker can grab the master key and open everything. SELinux is a security measure that says "even if you have the master key, you can only open the doors listed in our policy for this specific key." 
# Find all setuid binaries on an ECU
find / -perm /4000 -type f 2>/dev/null

# Good ECU result — minimal or zero setuid binaries:
# /usr/bin/passwd   (if password login is needed — often removed on headless ECUs)
# /usr/bin/sudo     (removed on production ECUs)

# Bad ECU result:
# /opt/oem/diag_tool  (setuid root with unknown code — massive risk)

7 — Attack Scenario: setuid Exploit → Root → DAC Bypass → SELinux Blocks

Scenario: Attacker finds a setuid binary with a stack overflow vulnerability

An ECU ships with a diagnostics tool owned by root with the setuid bit set. An attacker on the OBD-II port exploits a buffer overflow in this tool.

1
Attacker connects via OBD-II / UDS interface
Using a diagnostic laptop connected to the OBD-II port, attacker sends a malformed UDS service request (0x27 SecurityAccess with oversized seed response) to the diagnostics daemon.
2
Stack overflow → code execution as root (UID=0)
The diagnostics binary is setuid root and has a stack overflow. Attacker triggers it, overwriting the return address with shellcode. The shell runs as UID=0 (root) because of setuid. DAC is now bypassed — root can read/write anything.
3
Attempt to read private OTA signing key
Attacker tries: open("/etc/ota/private.key", O_RDONLY). DAC says: UID=0, file owner=ota_user, permission=r--------. Root bypasses this check. DAC ALLOWS. But…
4
SELinux blocks: wrong domain for this resource
The process is still running in the SELinux domain of the diagnostics tool: diag_svc_t. SELinux checks: does diag_svc_t have read on ota_key_t? Policy says NO. Kernel returns -EACCES. AVC denial logged with: scontext=diag_svc_t tcontext=ota_key_t tclass=file.
5
Attempt to open CAN socket for frame injection
Attacker tries: socket(AF_CAN, SOCK_RAW, CAN_RAW). DAC: root can do anything with sockets. DAC ALLOWS. But…
5
SELinux blocks: diag_svc_t cannot create CAN sockets
SELinux policy does not grant diag_svc_t the create permission on can_socket class. Kernel blocks it. AVC denial logged. The CAN bus is safe.
6
Attack contained — V-SOC alerted
The attacker has root UID but is still confined to the diag_svc_t SELinux domain. They can only access what the diagnostics service is legitimately allowed to access. The OTA keys, CAN bus, and safety partition are untouchable. AVC denials trigger alerts in the Vehicle Security Operations Centre.

8 — DAC vs MAC: Why SELinux Exists

PropertyDAC (Traditional Linux)MAC (SELinux)
Who sets rulesFile owner (discretionary)System administrator / policy author (mandatory)
Root bypassUID=0 bypasses most checksUID=0 does NOT bypass SELinux
GranularityRead / Write / Execute on owner/group/othersPer-operation, per-type (hundreds of permissions)
Compromise impactAttacker inherits all owner's permissionsAttacker confined to current SELinux domain
Configurationchmod, chown on each filePolicy files compiled and loaded into kernel
Log on denialNo loggingAVC denial logged with full context
Cross-file trackingNo — each file independentYes — domain transitions tracked system-wide

9 — Intrusion Detection & Forensics

Signs of privilege escalation or lateral movement visible via DAC + SELinux:

  • AVC denial: scontext=diag_svc_t tcontext=ota_key_t tclass=file { read } — diagnostics accessing OTA keys
  • AVC denial: scontext=can_gw_t tcontext=selinux_config_t tclass=file { write } — CAN gateway trying to modify SELinux policy
  • Unusual setuid binary execution: ausearch -m AVC -k setuid_exec
  • Root process in unexpected SELinux domain: ps -Z | grep "diag_svc_t"

Post-incident investigation steps:

# Find all setuid binaries (potential exploit vectors)
find / -perm /4000 -ls 2>/dev/null

# Find files with world-writable permissions (misconfiguration)
find / -perm -002 -type f -ls 2>/dev/null

# Check SELinux context of suspicious processes
ps -eZ | grep "unconfined\|unlabeled"

# Search AVC denials involving UID escalation period
ausearch -m AVC --start $(date -d '1 hour ago' +%H:%M:%S)

# Check which user a process is running as
cat /proc/PID/status | grep -E "^(Uid|Gid)"

ECU DAC hardening checklist (defence-in-depth with SELinux):

  • Remove all setuid/setgid binaries not strictly needed (sudo, su, many util-linux tools)
  • Run every daemon as its own dedicated UID (not root)
  • Set squashfs rootfs to ro mount option in /etc/fstab
  • Set /proc/sys/fs/protected_hardlinks = 1 and protected_symlinks = 1
  • Enable CONFIG_SECURITY_SELINUX_BOOTPARAM=n — prevent disabling SELinux from kernel cmdline
  • Use User= and Group= in all systemd unit files
  • Audit /etc/passwd and /etc/shadow for development accounts before production build
