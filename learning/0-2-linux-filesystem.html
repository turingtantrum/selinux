The Linux File System: Everything Is a File

Directory Tree · 7 File Types · inodes · xattrs · squashfs · genfscon · SELinux Labels

1 — Why Do We Need to Understand This?

SELinux labels are stored on files and directories. Every single object the kernel manages — regular files, device nodes, sockets, pipes, directories — is represented as a file in the Linux VFS (Virtual File System). That means SELinux must label every one of them.

On an automotive ECU running a read-only squashfs rootfs on an ARMv8 SoC, understanding how the file system works tells you exactly where SELinux labels live, how they survive a reboot, and what happens when a new file is created in a tmpfs at runtime.

💡 Analogy Linux treats everything as a file the way a city treats everything as an address. Buildings (regular files), pipes (named pipes), traffic cameras (device nodes), radio towers (sockets) — they all have an address. The city postal service (VFS) knows how to route requests to each one. SELinux is the city zoning board: every address has a zoning label, and the board decides which types of vehicles can visit which zones.

2 — The Directory Tree: The /root of Everything

Linux has a single directory tree rooted at /. There are no drive letters. Every storage device (eMMC partition, SD card, tmpfs) is mounted into this tree at a chosen location called a mount point.

Single unified directory tree — different filesystems mounted at different points

4 — Inodes: The File's Hidden Identity Card

Every file on disk has an inode (index node). The inode is a data structure inside the filesystem that stores everything about the file except its name and content: ownership, permissions, timestamps, size, and — crucially for SELinux — the location of any extended attributes.

💡 Analogy Think of a library. The book (file content) sits on a shelf. The library catalogue card (inode) records who wrote it, when it was filed, how thick it is, and which shelf slot it's in. The catalogue card also has a sticky note stapled to it (xattr) that reads "SELinux label: ota_config_t". The title on the spine (file name) is just in the directory — it points to the catalogue card number (inode number).
File name, inode metadata, and SELinux label are stored separately

5 — Extended Attributes (xattrs): Where SELinux Labels Live

An extended attribute (xattr) is a key-value pair stored alongside the inode. SELinux uses the xattr named security.selinux to store the security context of every file. The value is a string like:

security.selinux system_u:object_r:ota_config_t:s0
security.selinux system_u:object_r:can_device_t:s0
security.selinux system_u:object_r:selinux_config_t:s0

You can read and set xattrs with these commands:

# Read the SELinux label of a file
getfattr -n security.selinux /etc/ota/config.json
# or simpler:
ls -Z /etc/ota/config.json

# Restore a label to its policy-defined value
restorecon /etc/ota/config.json

# Set a label manually (rarely needed — prefer restorecon)
chcon -t ota_config_t /etc/ota/config.json

6 — squashfs: The Read-Only Rootfs on ECUs

An automotive ECU rootfs is almost always a squashfs image — a compressed, read-only filesystem. It is baked at build time, signed, and stored in a flash partition. The kernel mounts it at / on boot.

💡 Analogy squashfs is like a sealed, vacuum-packed box of meals that was packed in a factory and shrink-wrapped. You can open the box and eat (read files), but you cannot add, remove, or modify anything inside — it's factory-sealed. The seal is also tamper-evident: if the firmware validation fails, the bootloader refuses to load it. On an OTA update, the factory prepares a completely new box, validates it, and swaps it in at the next boot.

7 — Virtual Filesystems: /proc, /sys, /dev

These three directories do not correspond to any physical storage. They are virtual filesystems maintained by the kernel entirely in RAM. Every file inside them represents live kernel state.

/proc is a window into the running kernel and every process. It has no files on disk — the kernel generates the content on demand when you read() it.

Because /proc has no real inodes, SELinux labels it via genfscon rules in policy (see Section 9).

/sys (sysfs) exposes the kernel's internal device model as a file tree. Every driver, bus, power domain, and GPIO is represented as a directory with readable/writable files.

8 — unlabeled_t: What Happens Without a Label

When SELinux encounters a file with no security.selinux xattr (or a filesystem that doesn't support xattrs), it assigns the type unlabeled_t. Policy almost never allows processes to access unlabeled_t files, so this effectively blocks access to any unlabeled resource.

ECU Scenario: unlabeled_t as a Safety Net

An attacker manages to inject a file into the ECU's writable /data partition without setting a proper SELinux label (perhaps via a partially-exploited file write vulnerability). The file gets unlabeled_t. The OTA daemon, CAN gateway, and diagnostics server — none of them have policy rules to access unlabeled_t. The injected file is harmless: even if the attacker can create it, no ECU service will execute or read it.

9 — genfscon: Labeling Virtual Filesystems

Since virtual filesystems like /proc and /sys don't have inodes with xattrs, SELinux labels them using genfscon rules in policy. A genfscon rule maps a filesystem type + path prefix to a security context.

; In CIL policy — label /proc entries
(genfscon "proc" "/"           (system_u object_r proc_t s0))
(genfscon "proc" "/net"        (system_u object_r proc_net_t s0))
(genfscon "proc" "/sys/kernel" (system_u object_r proc_kcore_t s0))

; Label sysfs SELinux interface
(genfscon "sysfs" "/kernel/security/selinux"
                               (system_u object_r security_t s0))

; Label CAN devices under /dev
(genfscon "devtmpfs" "/can"    (system_u object_r can_device_t s0))

genfscon rules are evaluated every time the kernel looks up a label for a virtual file. They require no on-disk xattr storage — the label is computed from the path at lookup time.

10 — Attack Scenario: Rootfs Tampering & Label Forgery

Scenario: Attacker tries to plant a backdoor binary in the ECU rootfs

1
Offline rootfs extraction Attacker extracts the firmware binary from a stolen ECU using JTAG or SPI flash dumping. They unsquash the rootfs, add a backdoor binary, and re-squash it.
2
dm-verity / Secure Boot blocks loading The bootloader (U-Boot with FIT image verification) checks the squashfs signature. The tampered image signature doesn't match. Boot is aborted. The attacker's rootfs is never mounted.
3
Runtime write attempt (via exploited daemon) Attacker instead exploits a running daemon to try to write a new binary to /tmp/backdoor.
4
SELinux blocks exec on tmpfs binary Even if the write to /tmp succeeds (tmpfs is writable), files there get label tmp_t. No domain has policy to execute a tmp_t file on this ECU. execve() is blocked. AVC denial logged.
5
No label → unlabeled_t → no access Even if the attacker writes a file without an xattr, it gets unlabeled_t. No domain has access to unlabeled_t. The file exists but is unreachable.

11 — Intrusion Detection & Forensics

  • AVC denials for tcontext=unlabeled_t — file planted without proper label
  • AVC denials on execve from tmp_t or var_t — execution attempt from writable area
  • AVC denials accessing /dev/mmcblk0 directly — trying to write raw flash
  • Repeated getfattr calls on key files — label reconnaissance

After an incident:

  • find /data -xattr security.selinux -name "unlabeled_t" — find unlabeled files (planted without proper label)
  • Compare squashfs hash against build server hash — detect offline tampering
  • ls -Z /tmp /var/run — identify files with suspicious or missing labels
  • AVC log timestamps correlate with OTA update window — narrow down attacker's access window
